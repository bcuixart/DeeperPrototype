HOTDOG FEST - NETWORKING OVERVIEW
=================================

Goal: online multiplayer, up to 8 players, one host who is also a normal player.
Casual game, friends at low ping first, public lobbies later. Not over-engineered.
This file explains how the networking code is organised so it is easy to pick up again.

Current state (protocol version 9):
  lobby, level start, input exchange, clock sync, host snapshots with rollback/replay
  reconciliation, sand sync, provenance-based scoring, timed rounds, disconnects in game.
  NOT done: online menus (cursors, between-rounds menu).


1. FOLDER STRUCTURE
-------------------

src/Network/
    Transport/
        ITransport.hh            Generic transport interface + PeerId, Channel, NetEvent
        EnetTransport.hh/.cc     ITransport implemented with ENet
        LagSimTransport.hh/.cc   Decorator over any ITransport: latency, jitter, packet loss
    Protocol/
        ByteStream.hh/.cc        ByteWriter / ByteReader: values <-> bytes
        NetworkProtocol.hh/.cc   Game messages: MsgType, Encode*/Decode* functions
    NetworkManager.hh/.cc        The only thing the game talks to
    NetworkTypes.hh              Shared plain data and constants (see section 3)
    RemoteInputBuffer.hh/.cc     Inputs received from other slots, indexed by tick
    ClockSync.hh/.cc             Keeps the client's tick ahead of the host's

src/Level/
    LevelNetworkSync.hh/.cc      Snapshot building, history, rollback + replay
    NetworkLevelObjectDynEntState.hh   Per-object state sent in snapshots
    RoundManager.hh/.cc          Round timer, scores, round end (host authority)

    Tests/ (standalone executables, not part of the game)
        NetTest.cc               Raw transport roundtrip
        LobbyTest.cc             NetworkManager lobby test: --host [n] | --join [address] [n]


2. LAYERS AND DEPENDENCY RULES
------------------------------

    Game  ->  NetworkManager  ->  NetworkProtocol / ByteStream
                              ->  ITransport  ->  EnetTransport (or LagSimTransport -> EnetTransport)

Rules (they keep the code replaceable):
  - Transport knows NOTHING about the game or the protocol. It only moves byte arrays.
  - Protocol knows NOTHING about the transport. It only converts messages <-> bytes.
  - NetworkManager is the only place that uses both. It does not know game event kinds.
  - The game only includes NetworkManager.hh and NetworkTypes.hh.
  - enet/enet.h is included ONLY in EnetTransport.cc (it pulls in windows.h/winsock2.h,
    which clash with raylib). EnetTransport.cc must never include raylib.
  - Anything received from the network is untrusted: decoders check ByteReader::Ok() and
    the host validates contents.

Transport layer
  ITransport: StartHost, Connect, Disconnect, Send, Poll, GetRttMs.
  - Peers identified by PeerId (uint16). On the client, the server is one peer.
  - Two channels: Reliable (ordered, retransmitted) and Unreliable (inputs, snapshots, pings).
  - EnetTransport: channel 0 = reliable, channel 1 = unreliable.
  - LagSimTransport only delays OUTGOING packets, so with both sides using it RTT is about
    2 x latency. Loss only affects the Unreliable channel. Reliable packets and Disconnect keep
    their relative order. Needs Poll() to release delayed packets.
  - A future SteamTransport must implement the same interface.


3. MACHINES, SLOTS, CONSTANTS (NetworkTypes.hh)
-----------------------------------------------

  - A "machine" is one connected computer. machineId 0 is always the host.
  - A machine owns 1..4 slots (kMaxPlayersPerMachine). At most 8 slots (kMaxSlots == MAX_PLAYERS).
  - Slot numbers are global and identical on every machine.
  - kInputRedundancy = 6, kSnapshotInterval = 6 ticks, kMaxSnapshotBytes = 1000,
    kMaxEventBytes = 255, kNoMachine = 0xFF, kProtocolVersion = 9, kNumDogTypes = 5.
  - Bump kProtocolVersion whenever a message layout changes (Hello rejects mismatches).


4. MESSAGES (NetworkProtocol)
-----------------------------

  Every message starts with 1 byte = MsgType.

    Hello      client -> host   reliable    u16 version, local dog types (each < kNumDogTypes)
    Welcome    host -> client   reliable    u8 machineId
    Reject     host -> client   reliable    u8 reason (VersionMismatch, LobbyFull, BadRequest)
    LobbyState host -> clients  reliable    per slot: machineId + dogType
    StartLevel host -> clients  reliable    lobby, u32 spawnSeed, u32 roundTicks, u32 levelHash,
                                            level name (only [A-Za-z0-9_-], validated on decode)
    Input      both ways        unreliable  tick + per slot the last 6 inputs (redundancy)
    TimePing   client -> host   unreliable  client timestamp
    TimePong   host -> client   unreliable  host tick + echoed timestamp (gives RTT + host tick)
    Snapshot   host -> clients  unreliable  u32 tick + u16 len + bytes (see section 7)
    GameEvent  both ways        reliable    u8 kind + u8 len + bytes (see section 9)

  GameEvent is generic: NetworkManager only moves {kind, bytes}. Game code defines kinds
  (enum RoundEvent in RoundManager.hh: ScoreChanged = 1, RoundEnd = 2, PlayerLeft = 3).
  Host -> everyone: HostBroadcastEvent. Client -> host (an INTENT, host validates):
  SendEventToHost. Host reads them with PopEvent (includes fromMachine).


5. CONNECTION FLOW
------------------

  Client: Join() -> Connecting -> transport Connected -> sends Hello
  Host:   Hello -> validates -> allocates slots -> Welcome -> broadcasts LobbyState
  Client: Welcome -> InLobby; LobbyState -> updates lobby
  Host presses ENTER: HostStartLevel(name, roundTicks, levelHash) -> StartLevel to everyone, state InGame.
  Each client hashes its own level file (ComputeLevelHash in GameManager.cc, FNV-1a, ignoring
  '\r') and leaves with a message if it differs from the host's. Its dog then turns grey.
  A peer that connects but does not send a valid Hello within kHelloTimeoutMs (3 s) is kicked.
  A Hello with a dogType >= kNumDogTypes is rejected (BadRequest).
  Rejected: Reject, then disconnect; client goes to Failed with the reason.
  Client leaves in lobby: host frees its slots, broadcasts LobbyState.
  Host leaves: clients go to Failed ("host closed the room") and return to the menu.
  Joining a level that already started is rejected on purpose. There is no re-entry.

  NetworkManager states: Idle, Connecting, InLobby, InGame, Failed.


6. DETERMINISM AND THE TICK LOOP
--------------------------------

  The level is simulated on EVERY machine with the same fixed timestep (1/60 s). Rules:
  - Only the fixed timestep drives the simulation (accumulator in main.cc, scaled by
    GetTimeScale). Never use GetFrameTime / GetTime / GetRandomValue inside the simulation.
  - Randomness: DeterministicRng / DeterministicShuffle, seeded by the host's spawnSeed.
  - Objects are created in the same order everywhere (dogs by ascending slot). The order of
    LevelManager::_levelObjects is the identity of an object in snapshots.
  - IsKeyPressed and similar are frame-level only: read them once per render frame, never
    inside the fixed loop. PollNetwork() runs once per render frame, before the fixed loop.
  - Check for violations with:
      grep -rnE "GetTime\(|GetFrameTime|GetRandomValue|rand\(|IsKey|IsGamepad|std::chrono" src/

  Per tick order: LevelManager::Update (every object's Update) -> PhysicsManager::Update
  (reset grounded, gravity, force fields, move/resolve X then Y, overlaps).

  Tick numbering is shared: client tick N means host tick N.


7. INPUTS, CLOCK SYNC, SNAPSHOTS AND ROLLBACK
---------------------------------------------

Inputs
  - Level input byte: bit0 jump, bit1 dig, bit2 bark, bits 3-7 X axis (centre 16).
    Neutral = kNeutralLevelInput (16 << 3).
  - Every machine sends its slots' inputs each tick (unreliable, last 6 inputs per packet).
  - RemoteInputBuffer::Get(slot, tick, neutral, &exact): ring of 64, looks back 8 ticks,
    repeats the last known input, neutral after 30 ticks without news. It NEVER waits.
  - Local slots use their own input immediately (local feel is always instant).

Clock sync (ClockSync)
  - Client estimates RTT from TimePing/TimePong and runs ahead of the host by RTT_ticks + 2.
  - So the host sees client inputs exactly (they arrive before the host reaches that tick),
    while the client always sees the host's inputs ~RTT late and PREDICTS them.
    "remote inputs not exact: 120/120" in the debug print is normal on a client.

Snapshots (host -> clients, unreliable)
  - Every kSnapshotInterval ticks, plus an immediate extra one when sand changes.
  - Content: state of ALL net bodies after tick T + the sand-broken bitset.
  - Body state (NetworkLevelObjectDynEntState): x, y, vx, vy, mode, flags, aux, cause, depth,
    t0..t3. Meaning of flags/aux/t0..t3 depends on the object type (dog, ball, hydrant);
    see NetGet / NetSet of each class. WriteBody/ReadBody keep the field order.
  - Bodies are the objects whose NetGet() returns true, in creation order. Sand tiles are not
    bodies: they travel as a bitset over the row-major list of 'S' tiles.
  - Slopes are NOT synced (their behaviour follows from the dog snapshots).

Rollback + replay (LevelNetworkSync, client only)
  - The client keeps a 64-tick history of {tick, bodies, sand}.
  - On a snapshot for tick T it compares the host's state at T with its own history at T.
    If a body differs (pos > 0.02, vel > 0.1, mode or flags) or sand differs, it ADOPTS the
    host's state at T and re-simulates T+1..latest with ReplayTick, re-recording history.
    Replay re-queries remote inputs with whatever fresher information arrived.
  - L - T is constant (about 8 ticks). Errors of 1-2 tiles at ~100 ms RTT are inherent
    prediction errors (speed x lag) and are expected.
  - ALL state that affects future simulation must be in the rollback set (NetGet/NetSet):
    dogs, ball, hydrant (restored through Activate/Deactivate). That includes carried state
    like _isGrounded and surface type, jump/coyote timers and the *Prev inputs.
    If you add a dynamic object or a new field that changes behaviour, add it to NetGet/NetSet
    and check that "[rollback]" lines stay quiet when idle.
  - Rendering side effects (sounds, particles) triggered in Update would be repeated during
    replay. If that becomes a problem add a "replaying" flag.

Visual smoothing
  - Rollback moves objects instantly. To avoid snapping, every LevelObject has a render-only
    _renderOffset: after a snapshot is applied, (old position - new position) is added to it
    and it decays exponentially (kRenderOffsetDecay = 12 /s, about 80 ms). Jumps above 4 tiles
    are not smoothed. Dog::Render adds the offset. Other objects can do the same.


8. AUTHORITY AND SCORING
------------------------

Authority rule
  - The host decides. Offline behaves like a host.
  - Client applies a sand break immediately only if the CAUSE of the break is one of its own
    slots (LevelManager::CanApplyBreak(cause)). Otherwise it waits for the host's sand bitset
    in the next snapshot. Hydrants and balls need no special rule: rollback self-heals them.

Provenance (who is responsible for an interaction)
  - Every LevelObject has GetCauseSlot() (kNoCause = 0xFF) and GetChainDepth().
  - Dog: cause = its own slot, depth 0. Ball kicked by a dog: cause = dog, depth + 1.
    Hydrant: Activate(cause) -> depth + 1 (also when dug). Water forwards its hydrant's
    cause. A ball inside a force field takes the field's cause, depth + 1 (re-stamped each tick).
  - Points = basePoints + cause->GetChainDepth() (sand base = 1), so the number of steps in the
    chain is the score: dig = 1, kicked ball hits sand = 2, ball launched by a dug hydrant = 3,
    ball launched by a hydrant activated by a ball you kicked = 4.
  - Balls forget their cause when they have completely stopped (grounded and almost no speed).
  - Dogs flung by an interaction should borrow the cause (planned, see section 11).

Rounds (RoundManager)
  - durationTicks is carried in StartLevel. Time end is deterministic: endTick.
  - Only host/offline award points (LevelManager::NotifyScore -> GameManager::OnScore).
    The host broadcasts ScoreChanged with ABSOLUTE scores (idempotent). Clients just display.
  - The host can end early with EndEarly (e.g. last bone taken). It broadcasts RoundEnd
    {endTick, scores} once. A client freezes at its own tick >= endTick; if it overshot it
    RestoreTo(endTick - 1) and sets its level tick to endTick.
  - Known limitation: at a time-based end the client's final picture is predicted.


9. DISCONNECTS IN GAME
----------------------

  - Client leaves cleanly: ENet reports Disconnected. Client crashes or cable pulled: the host
    watchdog (kSilenceTimeoutMs = 4 s without ANY message from a machine in InGame) drops it.
  - NetworkManager::HostDropMachine removes the peer, keeps the lobby slots (dog stays in the
    level and keeps its score) and queues the slots in _leftSlots (PopLeftSlot).
  - GameManager broadcasts GameEvent RoundEvent::PlayerLeft (3, payload = slot). Everyone calls
    LevelManager::SetSlotGone -> the dog is drawn grey. _isGone is visual only.
  - The gone dog receives neutral inputs automatically (RemoteInputBuffer). No tick has to be
    announced: any tiny difference between machines is fixed by snapshots.
  - Host leaves: every client goes to Failed and back to the menu.


10. DESIGN DECISIONS AND LESSONS LEARNED
----------------------------------------

  - ENet reports a failed connect only after 10-30 s: NetworkManager has its own 5 s timeout.
  - A Disconnected event is not guaranteed. Use timeouts for detecting missing players.
    Disconnect is a courtesy. Use enet_peer_disconnect_later so queued data goes out first.
  - Leave() blocks ~200 ms to let disconnect messages go out. Only call it when leaving.
  - Reject must arrive BEFORE the disconnect (order of Send and Disconnect matters).
  - Additive delta corrections from snapshots put dogs inside solids and made them fall
    through the floor. The fix was rollback + replay, not blending. Do not go back.
  - isGrounded cannot be derived: it is real carried state and must be in the snapshot.
  - Pop the snapshot OUTSIDE the input-reading loop in PollNetwork.
  - The lobby message must include dogType (it was missing once).
  - A resting ball never has vy == 0 (gravity every tick): rest thresholds must be a bit above
    kGravity * dt.
  - Commented-out debug printfs are intentional (the author re-enables them when needed).


11. KNOWN LIMITATIONS / TODO
----------------------------

Robustness
  - SlotInfo only has machineId and dogType. Later: name, colour.
  - ComputeLevelHash hardcodes the level path (assets/levels/<name>.dgl): keep it in sync with
    LevelManager::LoadLevel, or expose one shared GetLevelPath(name).
  - Dog::SetDogType still uses '% 5': replace with kNumDogTypes.

Gameplay networking
  - Dogs as interaction agents: a dog flung by a hydrant/ball should BORROW the cause
    (slot, depth + 1) while out of control and go back to its own slot / depth 0 when it
    recovers control (grounded and horizontal speed back to walking speed). Ball-ball overlap
    propagating cause is optional. Use the same "is flung" test for losing control,
    bouncing off walls and forgetting the cause.
  - Own score appears with ~RTT delay on clients (could show a predicted value).
  - Sand history is not rolled back per tick (it is reconciled approximately).
  - A final snapshot at round end would remove the predicted final picture.
  - Level loading robustness: deferred until the level format is finalised.

Menus (not started)
  - Cursors per slot: position stream (unreliable, local immediate, remote interpolated);
    clicks are reliable intents validated by the host (e.g. only the round winner can pick
    the next mode).
  - Game-phase state machine driven by host reliable events:
    lobby -> level -> between-rounds menu (scores, winner picks mode) -> end of game.
  - Lobby with cursors for dog selection / ready.
  - Join screen: dog selector, name keyboard with recent names, local/online choice.
  - Later: public lobbies, SteamTransport behind ITransport.


12. HOW TO TEST
---------------

  Build:  make network_tests      (standalone transport/lobby tests)

  Lobby:  lobbytest --host 2        (host with 2 local players)
          lobbytest --join 127.0.0.1 1

  In the game: run one host and several clients on the same machine. Use LagSimTransport to
  simulate lag (80 ms is a harsh value; real friends at low ping are well below that).
  Useful checks:
    - Idle dogs converge to the same position on every machine.
    - "[rollback]" lines appear only when something really diverged.
    - Sand, ball and hydrant state match everywhere after the action ends.
    - Scores: "[punts]" on the host shows who gets what (dig +1, kicked ball +2, ...).
    - Close a client window and kill a client process: its dog turns grey on everybody
      (4 s for the kill case).
    - Close the host: clients return to the menu. Joining a started level is rejected.
